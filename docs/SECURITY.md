# Security

This document covers what aesx protects, what it does not, the reasoning behind the design,
and how to report a vulnerability. The byte-level specification is in [FORMAT.md](FORMAT.md).

## Reporting a vulnerability

Please do not open a public issue for a security problem. Use GitHub's private vulnerability
reporting instead: **Security → Report a vulnerability** on the repository page, or
<https://github.com/yohasacura/aesx/security/advisories/new>. You will receive an
acknowledgement within seven days. Fixes ship as a new release with a CHANGELOG entry that
credits the reporter, unless they prefer to stay anonymous.

## What aesx protects

An `.aesx` file keeps its contents **confidential** and **tamper-evident** against anyone who
obtains the file but does not know the password: a lost laptop or USB stick, a cloud-storage or
e-mail provider, a backup operator, or an attacker who copies the file today and keeps attacking
it for years.

For every file:

- **Confidentiality.** AES-256 in GCM mode, with a key that exists only for that file. The key is
  derived from the password and a random 128-bit salt, so two files encrypted with the same
  password share no key material.
- **Integrity and authenticity.** Every 1 MiB chunk carries a 128-bit authentication tag that is
  bound to the chunk's position, to the file header, and to an end-of-file marker. Modified,
  reordered, duplicated, removed or appended chunks, a swapped header, truncation at any point,
  and chunks spliced in from another `.aesx` file are all detected, and the file is rejected.
  Plaintext is released only after its tag verifies, and the command-line tool discards any
  partial output.
- **Resistance to password guessing.** Each guess costs the attacker one PBKDF2-HMAC-SHA256 run
  of 600 000 iterations (configurable with `--iterations`) for each file, and the per-file salt
  makes precomputed tables useless.

## What aesx does not protect

- **The password itself.** Anyone who learns it can decrypt the file. A short password, a
  password reused elsewhere, or one that appears in a breach list is by far the weakest link.
- **The computer you use.** Malware, a keylogger, or another user with administrator rights on
  the machine where you type the password can read the password, or read the plaintext before
  encryption and after decryption. No file-encryption tool can defend a compromised endpoint.
- **Metadata.** The output name is derived from the input name, the output size is the input size
  plus 29 bytes plus 16 bytes per chunk, and timestamps are whatever the filesystem records.
  Anyone can see that a file is an `.aesx` file and how large the original was. Put files in an
  archive first if names or the number of files are sensitive.
- **Plaintext left elsewhere.** The original (unless you pass `--delete`), earlier copies,
  cloud-sync caches, editor backups, swap and hibernation files, and the recycle bin may still
  hold the data. `--delete` is an ordinary deletion, not a secure wipe; on modern SSDs no
  user-space tool can promise a wipe. Full-disk encryption (BitLocker, FileVault, LUKS) is the
  right tool for that layer.
- **Availability.** An attacker who can modify the file can always destroy it. aesx guarantees
  that you will notice, not that the data survives.

## Choosing a password

Key stretching slows an attacker down; it cannot make a weak password strong. Against the default
600 000 iterations, a modern GPU manages on the order of ten thousand guesses per second.
Exhaustive search with a hundred such GPUs:

| Password                                        | Entropy  | Time to try every possibility |
| ----------------------------------------------- | -------- | ----------------------------- |
| 8 random lowercase letters                      | ~38 bits | days                          |
| 4 random dictionary words (Diceware)            | ~52 bits | about a century               |
| 12 random characters (letters, digits, symbols) | ~79 bits | billions of years             |
| 6 random dictionary words (Diceware)            | ~78 bits | billions of years             |

Use at least five randomly chosen words or twelve random characters, generated by a password
manager or dice, and never reuse the password elsewhere. Raising `--iterations` scales the
attacker's cost linearly, and your own wait time with it.

## Design decisions

**Only platform cryptography.** aesx contains no cryptographic code of its own. AES-GCM, PBKDF2,
HMAC-SHA256 and the random number generator all come from the .NET base class library, which
delegates to Windows CNG, Apple CryptoKit, or OpenSSL on Linux. Those implementations are
hardware-accelerated, constant-time where it matters, and reviewed far more widely than anything
a small project could write. The shipped binary contains no third-party packages at all, which
also keeps the supply chain short: the .NET SDK and this repository.

**AES-256-GCM.** An authenticated cipher is non-negotiable; unauthenticated modes such as CBC
have a long history of padding-oracle and bit-flipping attacks. GCM is the AEAD available in every
platform library, is accelerated by AES-NI and ARMv8 instructions, and reaches gigabytes per
second. Its well-known weaknesses, nonce reuse and the 64 GiB per-nonce limit, are both ruled out
by construction here (see below).

**PBKDF2-HMAC-SHA256, 600 000 iterations.** A memory-hard function such as Argon2id would resist
GPU attacks better, but the .NET base class library does not provide one, and taking a
third-party implementation would contradict the zero-dependency goal while adding exactly the
kind of code that must not be wrong. PBKDF2 at this iteration count is the OWASP recommendation
and is FIPS-approved. A future format version can carry a KDF identifier if the platform gains
Argon2.

**Independent 1 MiB chunks.** Encrypting a file as a single GCM message would require buffering
the whole file to verify the tag before releasing any plaintext, which limits file size and
memory. Chunking gives streaming with constant memory, lets a wrong password fail after the
first chunk, and keeps every GCM message far below the 64 GiB limit. The classic problem with
chunking, that an attacker can reorder, drop or truncate chunks, is addressed by binding the
chunk index and an "is last" flag into the authenticated data, so the decryptor refuses anything
but the original chunks in the original order ending where the original ended.

**Nonce = random prefix + counter.** Within one file the counter guarantees that no two chunks
share a nonce. Across files the random salt guarantees that no two files share a key, so nonce
reuse across files is harmless. The random 32-bit prefix is defence in depth, not a security
requirement. A file is limited to 2^32 chunks (4 PiB) to stay within NIST SP 800-38D.

**One key per file, from a per-file salt.** Several files encrypted with one password in one run
still get distinct keys, and compromising one file's key tells nothing about the others.

**Not compatible with AES Crypt.** The `.aes` format predates widespread AEAD support and
authenticates whole files rather than chunks. Reproducing it would mean reproducing its design
rather than its goals; aesx keeps the workflow and replaces the format.

## Implementation notes

- Keys, password bytes and chunk buffers are zeroed with `CryptographicOperations.ZeroMemory`
  once used. Passwords are read into character arrays, not strings, so that they can be wiped;
  a password given with `--password` arrives as a string from the operating system and cannot be.
  The garbage collector may have moved buffers before they were wiped, and the operating system
  may have swapped them out; full-disk encryption covers that residue.
- The password confirmation prompt compares in constant time (`FixedTimeEquals`).
- Hostile files cannot cause unbounded work: the iteration count in the header is capped at
  100 000 000, chunk sizes are fixed by the format, and no attacker-controlled length field is
  ever used for allocation.
- Output is written to a temporary file and renamed into place only after the last chunk has
  verified, so a wrong password, a corrupted input or a crash never leaves a partial file.
- Randomness comes from `RandomNumberGenerator`, the operating system's CSPRNG.
- Release binaries are built from tags by GitHub Actions, on the target platform, with the run
  publicly visible, and ship with `SHA256SUMS.txt`. The same binary can be rebuilt locally with
  one `dotnet publish` command ([BUILDING.md](BUILDING.md)).
- The binaries are not signed with a paid certificate, so Windows SmartScreen and macOS
  Gatekeeper warn on first launch. Building from source avoids the warnings entirely.

## Known limitations

- PBKDF2 is not memory-hard (see above).
- There is no public-key mode, key file, multi-recipient support, compression, or hiding of
  file size and names, and no secure-delete feature.
- `--password` exposes the password to other processes and to shell history; it exists for
  scripts that cannot use a pipe.
