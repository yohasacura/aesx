Why aesx

AES Crypt made the one-password workflow familiar. aesx keeps that workflow and rebuilds everything else: modern authenticated cryptography, no dependencies, and no surprises when something goes wrong.

Authenticated encryption

AES-256-GCM with a key derived by PBKDF2-HMAC-SHA256 from a random 128-bit salt for every file. A wrong password, a flipped bit, a missing chunk or a truncated file is detected and rejected; nothing is ever silently decrypted into garbage.

No third-party code

The product is one repository plus the .NET base class library. Every primitive comes from Windows CNG, Apple CryptoKit or OpenSSL: hardware-accelerated, widely reviewed, and not reimplemented here.

Completely offline

No network code, no telemetry, no update checks, no activation. The whole product is thirteen source files, a few thousand lines, and you can read all of them.

Any file size, constant memory

Data is processed in 1 MiB chunks, each authenticated on its own, so a 100 GB disk image needs the same few megabytes of RAM as a text file.

Hard to misuse

Never overwrites without --force, never leaves a half-written file or half-unpacked folder behind, verifies an encrypted file before --delete removes the original, and refuses same-file output up front.

Tested like it matters

A mutation fuzzer, a second reader for the format in another language, attack scenarios against the real binary, CodeQL and a dependency audit run on every change, on Linux, Windows and macOS.

Files, folders and pipes

A folder becomes one encrypted file and comes back as the folder it was, with its names and structure hidden inside. Data can also arrive on standard input and leave on standard output, so a database dump never touches the disk in the clear.

In the right-click menu

On Windows and macOS, aesx register adds Encrypt with aesx and Decrypt with aesx to Explorer or the Finder for your account. Select any number of files and folders; the password is asked once, in a small window. On a Mac, .aesx files then also open with a double-click.

Verify, then run

Each archive holds one executable plus LICENSE, README.md and CHANGELOG.md. Check it against SHA256SUMS.txt from the same release before unpacking; from 1.1.0 on, gh attestation verify also shows that the file was built by this repository's release workflow.

# Linux and macOS
sha256sum -c SHA256SUMS.txt --ignore-missing
# Windows PowerShell: compare with the line in SHA256SUMS.txt
Get-FileHash .\aesx-{{ version | default: "1.0.0" }}-win-x64.zip -Algorithm SHA256

The binaries are not signed with a paid certificate, so Windows SmartScreen and macOS Gatekeeper warn once; two clicks, or one xattr command, get past it. Or skip downloads entirely and build the executable yourself with one command and the .NET SDK:

dotnet publish src/Aesx.Cli/Aesx.Cli.csproj --configuration Release --runtime win-x64 --output out

Usage

Use the terminal or, on Windows and macOS, the right-click menu or a drop onto aesx. Names ending in .aesx are decrypted; everything else, folders included, is encrypted.

aesx <path>...                    encrypt; .aesx names are decrypted instead
aesx encrypt <path>... [options]  files to <file>.aesx, folders to
                                  <folder>.folder.aesx
aesx decrypt <file>... [options]  back to the original file or folder
aesx verify <file>...             check that files decrypt, write nothing
aesx info <file>...               what the header says, no password
aesx register | unregister        Windows, macOS: the right-click menu
aesx selftest                     run the built-in self-tests

-o, --output <path>    output file, an existing directory, or - for stdout
-p, --password <pw>    password on the command line (prefer the prompt,
                       AESX_PASSWORD or stdin)
-i, --iterations <n>   PBKDF2 iterations when encrypting (default 600000)
-f, --force            overwrite an existing output file
    --delete           delete the input after the output is written
                       (and, for encryption, verified)
-q, --quiet            no progress output
# backup.tar -> backup.tar.aesx, password asked twice
aesx encrypt backup.tar

# and back again
aesx decrypt backup.tar.aesx

# several files, one password
aesx photo1.jpg photo2.jpg notes.md

# a folder, and back
aesx encrypt photos
aesx decrypt photos.folder.aesx

# from a script; original deleted once verified
printf '%s\n' "$PASSWORD" | aesx encrypt nightly.sql --delete

# as a filter: nothing in the clear on disk
aesx decrypt notes.md.aesx -o - | less
pg_dump mydb | aesx encrypt - -o mydb.sql.aesx

The password comes from -p, the AESX_PASSWORD variable, the first line of a piped stdin, or an echo-free prompt, in that order. File names and passwords may use any script. Exit codes: 0 success, 1 failure, 2 usage error, 130 interrupted. Everything else is in the usage guide.

How it works

A fixed 29-byte header, then the file in 1 MiB chunks. Each chunk is encrypted and authenticated on its own and bound to its position, so a file streams with constant memory and still cannot be reordered, truncated or spliced.

header29 B
chunk 01 MiB + 16 B tag
chunk 11 MiB + 16 B tag
…
last chunk≤ 1 MiB + 16 B tag
header  = "AESX" || 0x01 || iterations (u32 LE) || salt (16 bytes) || nonce_prefix (4 bytes)
key     = PBKDF2-HMAC-SHA256(password, salt, iterations) -> 32 bytes
chunk_i = AES-256-GCM(key, nonce = nonce_prefix || i, aad = header || i || is_last)(plaintext_i) || tag_i

One key per file

The key is derived from the password and a random 128-bit salt, so two files encrypted with the same password share no key material, and no nonce is ever used twice under one key.

Position binding

The chunk index and an end-of-file flag are part of the authenticated data. Reordering, duplicating, dropping, truncating or appending chunks fails the tag check, and plaintext is released only after its tag verifies.

Nothing home-made

AES-GCM, PBKDF2, HMAC-SHA256 and the random number generator are the operating system's. aesx contains no cryptographic code of its own, and the format is small enough to re-implement from the specification in an afternoon: the repository holds a second reader in a hundred lines of JavaScript, so your files never depend on this one program.

The complete specification with a test vector is on the file format page; the threat model and the reasoning behind each choice are under Security.

When another tool fits better

aesx does one thing: it turns a password and a file or folder into one authenticated, encrypted file, and back. Some jobs call for something else.

Encrypting to a person, not a password

age encrypts to public keys, so nothing secret has to be shared beforehand. aesx has no public-key mode.

Compression and archives

7-Zip compresses, and its archives open in many other programs. aesx does not compress, and a folder it encrypts is unpacked by aesx or by tar.

A whole disk, or files you work in

BitLocker, FileVault, LUKS and VeraCrypt encrypt a disk or a volume that stays mounted while you work. aesx is for files you store or send.

Signatures and OpenPGP

GnuPG signs, manages keys and speaks the format mail programs and package managers expect. aesx only encrypts.

What aesx protects, what it does not, and its known limitations are spelled out under Security.

Coming from AES Crypt?

aesx is an independent project with no affiliation to AES Crypt, and it does not read or write .aes files. To migrate, decrypt with the AES Crypt you already have and encrypt with aesx. The day-to-day workflow is the same: one password, one file in, one file out, from the terminal or, after aesx register, from the right-click menu.
